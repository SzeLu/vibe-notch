## 修复：Claude Code 会话结束后 notch 仍显示"活动中"

用户环境：Claude Code 2.1.322（nvm 安装于 ~/.nvm/versions/node/v24.22.1/bin/claude），Vibe Notch v1.3.2。

### 结论 / 根因
- 终端的 "recap" 是 Claude Code 的 `awaySummaryEnabled` 会话回顾（JSONL `type=system, subtype=away_summary`），**不是 hook 事件**，app 完全没消费它；它总在 `stop_hook_summary` / `turn_duration` 之后写入，代表本轮确实已结束。
- `HookInstaller.detectClaudeCodeVersion()` 只探测 5 个固定路径，GUI app 的 PATH 里没有 nvm → 检测失败 → 回退 baseline 10 个 hook 事件，`PostCompact` / `StopFailure` / `PostToolUseFailure` / `PermissionDenied` / `SubagentStart` 全部没注册。缺 PostCompact 使 `.compacting` 无法退出（`.compacting` 属于 UI 的 isAnyProcessing，会一直转圈）。
- Claude Code 的 SessionEnd hook 共享 1.5s 预算；脚本为取 tty fork `ps`（2s timeout），结束事件容易被杀掉。
- hooks 并行执行、到达顺序不保证；`SessionStore.processHookEvent` 对已结束会话无防护，迟到的 Stop/PostToolUse/SubagentStop 会 `createSession` 重建僵尸会话（常为 `.processing`）。
- 状态机无超时自愈；兜底只靠 `kill(pid,0)`（pid 来自 hook 的 `os.getppid()`，可能是短命 shell 或僵尸）。
- 现场还发现 `/tmp/claude-island.sock` 是残留文件、连接被拒（app 当时未监听），该轮 hook 事件全部静默丢失。

### 改动（4 个文件）
- `Services/Hooks/HookInstaller.swift`：优先从最近 JSONL 的 `version` 字段解析版本；补充 PATH + nvm/volta/mise/bun/asdf 候选；SessionEnd hook 显式 `timeout: 10` 抬高共享预算。

## 修复 WorkBuddy 重复完成提示 + 收起态点击穿透（14:0x）

### 重复完成提示
- 根因：WorkBuddy 用转录 mtime 判 phase，一轮内工具调用之间的空档 >busyWindow 会误判 waitingForInput，恢复后又误判，导致多次弹跳/响铃/绿勾。
- 关键发现：`workbuddy.db` 的 `status` 字段（working/completed/error）是精确信号，比 mtime 可靠。
- 改 `WorkBuddyProvider`：status=working/pending/running/busy → processing；completed/complete/done/error/idle → waitingForInput（last_activity 超 10 分钟则丢弃，避免旧卡片堆积）；空/未知才回退 mtime。这样一轮只会产生一次 working→completed 转换。
- `NotchView.handleWaitingForInputChange`：新增 `completionNotifiedAt` 每会话 60 秒冷却，只有真正新完成才弹跳/响铃/显示绿勾；被抑制的重入不刷新 `waitingForInputTimestamps`，绿勾不会重复出现。记录 5 分钟过期防内存增长。
- `PollingAgentProvider`：已有 `stabilize()` 双向滞后（连续 3 次空闲才发布 waitingForInput，busyWindow 默认 60，WorkBuddy 90）。

### 收起态点击穿透
- 根因：`NotchWindowController` 收起态 `ignoresMouseEvents = true`，窗口收不到事件，`PassThroughHostingView.hitTest` 与 `.onTapGesture` 都失效；原全局监听依赖辅助功能权限不可靠。
- 方案：新增 `notchClickWindow`——一个仅覆盖 notch 的极小透明 NSPanel（level=mainMenu+5，ignoresMouseEvents=false），`NotchClickCatcherView.mouseDown` → `viewModel.notchOpen(reason:.click)`。主窗口保持收起态忽略事件（全屏穿透、不影响菜单栏/拖拽）。面板打开时 clickWindow orderOut，收起时 orderFront。
- 顺手修 `NotchPanel.sendEvent`：re-post 后恢复 `ignoresMouseEvents`（原来从不恢复，展开态点一次外部后按钮会全部失灵）；补上 leftMouseDragged/rightMouseDragged 的 re-post。

## 修复 issue #116：副屏展开面板后窗口无法拖拽（15:5x 之后）

### 根因
`NotchPanel.repostMouseEvent` 与 `NotchViewModel.repostClickAt` 把 NSScreen 全局坐标翻转到 CGEvent 坐标时，用 `NSScreen.main.frame.height` 做 Y 翻转。但 `NSScreen.main` 是「持有键盘焦点的窗口所在屏幕」，在多屏且副屏与主屏高度不同（如主屏 1920×1080、副屏 1600×900）时，它可能是高度不同的副屏。NSScreen 全局坐标系原点锚定在**主屏**（菜单栏屏，screens[0]）左下角，翻转必须用它（主屏）的高度，用错屏幕高度会把 re-post 的鼠标事件 Y 偏移，导致副屏上点标题栏拖拽永远落不到目标窗口、拖不动。Quit app 后恢复，因为不再 re-post。

### 改动（2 文件）
- `UI/Window/NotchWindow.swift` `repostMouseEvent`：Y 翻转改用 `NSScreen.screens.first?.frame.height`（主屏）。保留原 `convertPoint(toScreen:)`（这是 `convertPointToScreen:` 的 Swift 现名，本就正确，曾被误改成已废弃名、已还原）。
- `Core/NotchViewModel.swift` `repostClickAt`：同样改用主屏高度翻转。
- issue 提到的另两点（re-post 漏 dragged 事件、ignoresMouseEvents 不恢复）在上一轮提交 `7fabe0e` 已修，本次无需动。

### 验证
- 单独 `swiftc` 验证 API：`convertPoint(toScreen:)` 为正确现名；`NSScreen.screens.first` 返回主屏（height 1080），CGEvent 构造/Y 翻转均通过。
- 完整 `xcodebuild`（Debug + `-Xfrontend -disable-sandbox` + 禁用签名 + `IDEPackageSupportDisableManifestSandbox YES`）→ **BUILD SUCCEEDED** 零错误。
